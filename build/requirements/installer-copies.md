## Public

**The install** (steps `auth`, `acct`, `fresh`, `plan`, `r2`, `rel`, `gen`, `install`, `fleet`, `bind`, `ai`, `addr`, `verify`)

- **R13** Each member that reads captured bytes is bound to the instance's `CAPTURES` bucket.

**Custody and the release**

- **R24** An install never shares another copy's buckets and never overwrites its fleet workers in the same account.
- **R32** Until installs are isolated (R24), an install into an account that already holds a copy (either evidence bucket, or a fleet worker, present) is refused before anything is created, saying that one installation of Civicsmith per Cloudflare account is supported for now (R40).

#### T50 (T50-78): the binding, the sizes, an account that already holds a copy, the situations (N1148, N1150, N1157, N1162, N1170; DEC-282; `build/plan/install-situations.md`)

- **R62** (T50; N1148; DEC-282; K3471; S1; replaces R32's refusal; `installupdate`, `installalongside`, `installremove`, `installremoveconfirm` are the installer's own routes, not plane ops) **An account that already holds a Civicsmith is told and offered a way on.** When `fresh` (R5) finds the plane or either evidence bucket or a fleet worker of a copy present, nothing is created or changed (`screen.install.stopped.exists`) and the page `screen.install.exists.*` is drawn, offering three choices: update it (`screen.install.exists.update.*`; R55 requires its version `V`), install alongside it (R64) and remove it, then install (R65). The installer stays stateless (R27) and keeps no token: each choice, after the founder's consent on Cloudflare's page, is a new `POST /begin` carrying that choice in R2's cookie. Test: an account holding a copy draws the page and no write is made; each choice begins its own path. Control: with no choice made nothing is changed.
- **R63** (T50; N1148; DEC-282; Bob's K3471 and the doubt's (a)) **What is already here is read once, from the copy's own worker.** The page draws `screen.install.exists.whose` (the team's name as its members read it, and its address), `.release` (release, installed date, last used) and `.holds` (its counts: projects, documents, published cases and members), each as that copy's own worker answers the installer's one request, stored nowhere. A fact the worker does not answer (an older release, silent, refused) is drawn as not known, with the reason, never guessed; when it states no counts, the installer's own counts from Cloudflare's API (the copy's workers, container applications, and objects in its two buckets) are drawn in their place, and the page says the team's own were not available. Test: a stub copy answering name, release and counts draws all three. Control: a silent copy draws each as not known and still offers the three choices. (T51-128; N1239, K3864; `instance-setup` R95, T51-106) **The facts, the credential and the reason.** The copy's `op=bootstrap` states the seven facts as `instance-setup` R95 words them (flat scalars `team_name`, `installed_at`, `last_used_at`, `count_projects`, `count_documents`, `count_published`, `count_members`, the wire names of `account.mjs`' `FACT_KEYS`), **to a credentialed caller only**; the installer presents no credential to a copy it did not make (R19), so a copy answers it none of them, and the page draws each fact as not known and the installer's own counts (`installer.fallback.*`, the note that the team's own were not available) in their place. The reason a fact is drawn not known is one of two: the copy did not answer (no address, no reply, a reply that is no object) reads `installer.fact.unknown.silent` ("didn't answer when the installer asked"); a copy that answered without the fact (the key absent or `null`) reads `installer.fact.unknown.short` ("not known"), **never `installer.fact.unknown.older`**, because a copy that withholds the seven cannot be told from an older release (R95; no new key marks it), so nothing is claimed of its release. No path reads `installer.fact.unknown.older` after this (R72's equality note). The per-fact lines are `installer.fact.unknown.<team|installed|used|release|projects|documents|published|members|counts|whose>` and the counts' nouns `installer.holdings.<k>.one|other`. Test: a stub answering `version` only draws every fact with `.short` and no `.older`, and draws the fallback counts; a stub answering the seven (as a credentialed caller would be answered) draws them; a stub that never answers draws `.silent`. Control: the page has no sentence "an older release" for a copy that answered.
- **R64** (T50; N1148; DEC-282; MULTI-INSTANCE-ISOLATION rows 1–7; amends R5, R10, R12, R13, R24, R32) **Installing alongside uses names no other copy holds.** An install into an account that holds a copy asks a short name (R2's grammar, R41's permanence dialog) that no copy there holds, and names every account-wide resource by it: the evidence buckets `bio-captures-<slug>` and `bio-published-<slug>`; each fleet member's worker `<member>-<slug>`, with the plane's service bindings and every member's `PLANE` binding targeting that slug's workers; each container application by slug. Each member that reads captured bytes is bound to its own copy's `CAPTURES` bucket (R13); `fresh` (R5) probes the new slug's own names, so a copy under the older fixed names is no collision and is neither read nor changed by an alongside install (MULTI-INSTANCE-ISOLATION row 7). A copy installed under the older fixed names keeps them and its update (R17) finds it by its slug; every later install, an alongside one or the first into an empty account, uses per-slug names. So R13 holds (each member's `CAPTURES` binding, row 6) and R24 holds (no install shares another copy's buckets or overwrites its fleet workers, rows 1–5), and R32's one-per-account refusal no longer applies. Test: two installs into one fake account hold two disjoint sets of names and neither changes the other's bytes, bindings or buckets. Control: an install under a slug a copy already holds is refused before anything is created.
- **R65** (T50; N1148; DEC-282; S1) **Removal is guided, confirmed, and complete.** `installremove` (offered as `act.owed_installremove.label.install`) draws `screen.install.remove.*` as DEC-282 draws it: what would be deleted for good, which is everything the copy holds (`screen.install.remove.lost.records`, its holdings, projects, documents and published cases, read as R63 reads them: the copy's own, else the installer's own counts from Cloudflare's API), every member's account and sign-in (`.lost.members`), its own copies of what it published (`.lost.published`) and its address (`.lost.address`); that nothing is kept by surprise (`.keep`); the short name to type (`.type.label`, `.type.help`); and that nothing has been deleted yet (`.sub`). Nothing is deleted before `installremoveconfirm` (`act.owed_installremoveconfirm.label.install`), which only the typed short name enables. On it the installer deletes every resource the copy holds in the account (its workers with their Durable Objects, its container applications, its two buckets with their objects), names each deletion on the progress page, names any refusal with what remains, and, when the account is clear, continues to a new install (a new consent, R62). Test: the holdings listed equal what R63 reads (a silent copy lists the installer's counts and says the team's own were unavailable); a wrong short name deletes nothing; after the confirmation the account holds none of the copy's resources and the install runs. Control: `installremove` alone deletes nothing.
