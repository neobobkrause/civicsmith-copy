# instance-updates — requirements

**Status** · New 4 Nov 2026: split from `instance-setup` for size (its requirement lines alone are over the 70,000-byte cap; the split proposed by `instance-setup`'s job, attempt 1, in `docs/requirements-notes/instance-setup.md` on `job/instance-setup`), accepted by the coordinator (BOB) 4 Nov 2026; K617, K624. A new module, layer 11, directly after `instance-setup`, split by copy with no `from`. R1–R7 are `instance-setup`'s R88, R89, R90, R91, R92, R106, R110, copied verbatim with their marks and renumbered in the order of their old ids, meaning unchanged; each line says "moved from instance-setup:R<n>". `instance-setup`'s own restarted job removes and retires the moved lines there, naming their new ids, and never reuses them. A bare `R<n>` inside a moved line that names no module is a `instance-setup` id. The code this module owns today is the release-check, set-up-release and health-sender code in `bio-plane/src/setup.mjs` and `setup-fleet.mjs`: it moves here only once `instance-setup`'s job has retired the lines; until then this module's job implements here and leaves `instance-setup`'s code to its job.

## Public

### Purpose

The daily release check, its reads and acts, its tables, the clock, the set-up release and the health sender.

### Provides

- **R1** (moved from instance-setup:R88) (T48; N1047; K3158; K3189; draft-updates §2; `signatures` R45, R48; `scheduler` R8) **The daily check.** At start this module registers one `scheduler` consumer, `update-check`, due once a day at an hour and minute fixed once per group from a random value it draws and keeps (never from the slug or anything sent), so groups do not ask at once.
  - Each run fetches the release notice at Civicsmith's one fixed public address (`RELEASE_NOTICE_ADDRESS`, a constant of this module, BOB's at the job's START) with a plain GET through `host-governor`: it sends an `accept` header and one fixed user agent (`UPDATE_CHECK_USER_AGENT`, `Civicsmith-update-check/1`) and nothing else (no cookie, no `Authorization`, no `credentials` or `cache` option, no group name, slug, member or setting in the address, headers or body); at most 64 KiB read; no redirect followed (`redirect: "manual"`). The minute is a UTC minute of the day, drawn at first start and kept (`update_check_slot`); the first run is the first occurrence after the draw.
  - It accepts the notice only when `signatures.verifyReleaseNotice(notice, sig, running, RELEASE_KEYS)` answers `ok: true` (R17's `VERSION` the running version): signed by a release key in `NS_RELEASE_NOTICE`, well formed, and newer than the running version. A notice that verifies but names the release that runs, or equals the one already held, is not stored and records `none` (the steady state); one older than the running release, or older than the one held, records `NOT_NEWER` and is not stored, so an older notice replayed changes nothing.
  - The notes are held as plain text exactly as signed (`signatures` R47 caps each part at 8,000 characters) and are never interpreted as markup: no link, image or script in them is ever followed or drawn as anything but text.
  - Each run appends one check `{at, outcome}`: `found` (a new notice stored), `none` (nothing newer, or the same as the running or held release), or the refusal (`unreachable`, `MALFORMED`, `BAD_SIGNATURE`, `UNKNOWN_KEY`, `NAMESPACE`, `NOT_NEWER` and the like). A failed or tampered fetch stores no notice, raises no item and reaches no member; the next day's run tries again.
  - At each start, when `VERSION` differs from the last running version recorded, it records the release now running with the instant first seen.
  - Tests: a notice signed with a test key in the list is stored; controls: one character of its notes changed stores nothing and records `BAD_SIGNATURE`; an older correctly signed notice records `NOT_NEWER`; a notice naming the running release records `none`; the request carries no cookie, credential or slug.
- **R2** (moved from instance-setup:R89) (T48; N1047; DEC-226 (2), (3); K3189) **The reads.** `updateNotice({viewer})` (`op=updatenotice`), to administrators only (`NOT_AN_ADMIN`, `membership` R84, a machine included), answers what Settings › Updates draws:
  - `running`: `{version, installed_at, allowed_by}`, `allowed_by` the administrator whose `updatestart` chose that version, or null when none is recorded;
  - `last_check`: `{at, outcome}` (R88), or null before the first;
  - `ready`: the newest stored notice newer than the running version and not skipped, `{version, date, security, notes: {members, administrators, must_do}, signed: true, found_at}`, with `decision`, the latest decision on it (R90) or null; `ready: null` when there is none. A newer release replaces an unanswered older one, and a skip is final: an older unskipped notice does not return when the newest is skipped;
  - `earlier`: each release offered before, newest first, at most `earlier_limit` (50; `earlier_truncated` true when more are held), `{version, date, security}` with `installed_at` and `allowed_by`, or `skipped_at`, `skipped_by` and `reason`, or `replaced_by` (the newest version) for one superseded unanswered;
  - `holder`: who holds the group's hosting account, as `membership.hostingAccess` (its R11, R113) records it, and `viewer_holds`, read from `membership.hostingAccess`'s free text: true when it names the viewer by member id or handle as a whole word, false when it does not or none is recorded, `null` when membership cannot answer.

  `updateNoticeState()` (in-process, for `machinery-producers` R12 through the plane's composition) answers `{ok, running, ready, decisions}` for the newest ready release, naming no viewer: `ready` as `updateNotice` answers it, with `decision`, and `decisions` every decision on it oldest first, each carrying its `version` (`machinery-producers` reads them so); `ready: null` and `decisions: []` when none. Both write nothing and never throw; a store that does not answer is the store's silence (R43). Control: a member who is not an administrator is refused `NOT_AN_ADMIN`.
- **R3** (moved from instance-setup:R90) (T48; N1047; DEC-226 (2), (3); K3158; `op-grades` R40) **The administrator's choice.** Each act is an administrator's (`by` the control plane's stamp; `NOT_AN_ADMIN` first, a machine included), names the `version` it decides (`UPDATE_NOT_READY` unless it is R89's `ready` release), and appends `{version, kind, by, at}`, never changing an earlier decision:
  - `updateStart({version, by})` (`op=updatestart`) records `start` and answers `{ok: true, version, address}`: the installer's update page set to that release and no other (`INSTALLER_UPDATE_ADDRESS`, a constant of this module, BOB's at the job's START, with `?version=<version>`). The address carries no credential, slug or member. It is also the hand-off link an administrator without the hosting account copies (DEC-226 (3)). Nothing is installed by this act: the installer installs, with Cloudflare's consent (`installer` R55).
  - `updateLater({version, by})` (`op=updatelater`) records `later` with `until`: 14 days on, or, for a release marked `security`, the start of the next local day (`civil-time`) in the first active profile's zone, UTC when none states one (the `zone` used is answered). A newer release replaces it at once (`machinery-producers` R11).
  - `updateSkip({version, reason, by})` (`op=updateskip`) records `skip` with the administrator's `reason`, the trimmed text of 1 to 1,000 characters on one line, else `UPDATE_SKIP_NO_REASON`. A skipped release is never ready again; the next release is offered as usual.

  The codes `UPDATE_NOT_READY` ("That release is not the one ready to install. Nothing was recorded.") and `UPDATE_SKIP_NO_REASON` ("Say why your group skips this release: every administrator will see it. Nothing was recorded.") take C-64.32 and C-64.33, BOB's drafts, re-wordable by the design stream, awaiting T49's stamp (plan rule 5 (2)). Tests: each act recorded and answered by R89; controls: `updateskip` without a reason refused, nothing written; `updatestart` naming an older version refused `UPDATE_NOT_READY`.
- **R4** (moved from instance-setup:R91) (T48; N1047; K3158; DEC-226 (2)) The release notices, checks, running releases and decisions are this module's own tables, append-only, declared to `record-core` exempt from purge as R28's are (the group's own running, not the corpus). Nothing here sends anything about the group, and this module holds no credential that could deploy code.
- **R5** (moved from instance-setup:R92) (T50; N1113; K3363; `scheduler` R8; amends R88) **The update check is given its clock.** The `update-check` consumer's `tick(now, …)` hands the alarm's `now` to the check (`#runUpdateCheck`, called at `updateCheckTick`; `setup.mjs:1223`, `:3263`), and the check's recorded instant (`update_checks.at`, and the `at` it answers) is that `now`, not a read of the clock. So under a virtual clock the consumer's `wake` advances after its tick, and the plane test that K3363 names clears. Test: an alarm at a fixed `now` records that instant. Control: a check run outside an alarm (no `now` handed) reads the clock as before.
- **R6** (moved from instance-setup:R106) (fix round 10; K5182; `screens-settings` R73, R81; SCREENS-SETTINGS #19 J36 D3; amends R89; R95 unchanged) **Updates names the set-up release.** `updateNotice` (R89) also answers `setup`: `{version, installed_at}` of the oldest release `running_releases` records (R88's first sighting of the release the copy was set up with), else `null`. Test: a copy set up on one release then running a second answers the first as `setup` and the second as `running`; control: a copy on its first release answers the same release in both, and an empty table answers `setup: null`.
- **R7** (moved from instance-setup:R110) (T53; AD38; K5487; beside R88's `update-check`) **The health sender.** A scheduler consumer `health-send`, registered beside `update-check` (R88) and run once a day at a minute drawn and kept per store, asks `ai-use.healthReport` (`ai-use` R33). For each report it sends `POST` to the issuer's fixed `HEALTH_ADDRESS` (`ai-issuer` R26) through `host-governor`, with headers only `content-type` and the fixed user agent (as `ai-catalogue` R34: no cookie, `Authorization`, team name, slug or installed version), following no redirect; on a `2xx` it calls `healthSent`; any other answer leaves the day for the next run, and nothing else changes. With the switch off `healthReport` answers `null` and no request is made. Test: switch on with one day counted: one POST with exactly those headers and the body `healthReport` answered, then `healthSent`. Control: switch off makes no request; a `500` leaves the day unsent and the next run sends it.
