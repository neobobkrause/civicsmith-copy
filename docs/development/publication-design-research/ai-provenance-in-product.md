# AI-use provenance in the published case: what the product records today

Read at commit `e2edad2bacff79dbda277cfcb0abe5628caf1cc4` (origin/tranche, "Merge PR 480: bob/cap-splits-2 into tranche"). All paths are relative to the repository root; `CG` = `build/requirements/case-grammar.md`. Read only; nothing was changed.

**Key distinction first.** In case-grammar, a "passage" (`passages:`, `ungraded_passages:`, `typed_passages:`) is a **relied-on passage of a source document** (a quote with `content_id`, capture, extent and transcription chain), not a passage of the case's own prose (CG:115, CG:201-202). The case's own authored prose is a different set: the account sentences, the four statements (statement, subject justification, exclusions, what changed), the scope, the bias acknowledgement, carried outcomes, and the members' findings (claims, legs) carried as pinned bytes. Bob's "per passage, AI or human wrote it" most naturally targets that authored prose; the source-passage side already has partial AI provenance (see 1.k). The lane should name which set it means.

## 2. How a passage is identified, and whether that holds across editions

- **Source passages:** `content_id`, a 64-hex content address over capture sha, extent and chain (`content.md:15`, `:22` R5; CG:115 "so `content_id` recomputes"). It stays the same across editions while the capture, extent and chain stay the same. Rows also carry `(finding, ord)`. `ord` is the leg's position within the finding's basis, so it is not stable if the basis changes.
- **Account sentences and statements:** only `ord`, a running position in the document (`case-account/index.mjs:313-332`, `++ord`), plus `kind`. **There is no stable id for an authored sentence.** Inserting a sentence renumbers every later one, and editions share no identity for "the same sentence".
- **Statements:** completeness `statement` has `statement_sha` (`case-inputs` R2); what-changed has `statement_sha`, the SHA-256 of its body section text (CG:31). `whatChangedOf(fm, body)` reads `{statement, began_as, draft, adopted_as_drafted}` (CG:31), and docket R9(b) quotes it (`build/summaries/T53/docket.md:28`, docket R9). These are content hashes, so they identify text, not a lasting slot.
- **Sections:** fixed headings and the `SECTIONS` locators for re-authorable runs (CG R3, CG:22); no numbering.
- **Findings:** bundle id plus `version_sha` pin and member `edition` (`document.mjs:153-166`).
- **Case file manifest (CG R13, CG:64-80):** identifies **files** by path, SHA-256, bytes and part. The case document is one file (`case_document`), so the manifest has nothing below document level. The manifest check (`caseFileManifestCheck`) and case-import key on it (`build/requirements/case-import.md:29-34` R1).

## 3. Which signed bytes cover what

- **Case statement:** `caseRatifyStatement(caseId, edition, docSha)` = `bio-ratify-case <case> <edition> <docSha>\n` in namespace `bio-ratify` (`bio-plane/src/sshsig.mjs:344-345`). `docSha` is the SHA-256 of the **whole document text** (`bio-plane/src/publication/index.mjs:553`, `storeCaseDocument`; `build/requirements/ratification.md:23` R2, `:55`). The checker verifies over the carried `case_document` file's sha256 (`bio-plane/src/case-checker/check.mjs:335`, `:386`; `build/requirements/case-checker.md:21` R3). **So any field placed in the document's front matter or body is signed.** One exclusion matters for approvals only: `approvalSubjectSha` drops the R26 block so approvals name the document before the block (CG R26, CG:144). That affects what *approvers* see, not the case signature.
- **Findings and evidence:** each pinned finding and each evidence bundle is signed separately with `ratifyStatement(id, sha)` (`build/requirements/screens-publish.md:46` R13; `case-checker.md:21` R3). Anything recorded in a finding's bytes (for example a basis version's `run`, 1.m) is signed there, not in the case statement.
- **Case file manifest:** carries the case document's SHA-256 and every file's digest (CG:65). The manifest itself is not signed separately. It is bound through the case signature over `docSha` and the per-file digests.
- **Docket entry:** `docketStatement(caseId, seq, sha)` in namespace `bio-docket` over the canonical-JSON entry's SHA-256 (`sshsig.mjs:402-415`; `build/requirements/docket.md:47-57` R4). The entry has a closed field list: "carries these fields and nothing else" (`docket.md:59-68` R6). It holds group prose (`summary`, `what_changed`, `reason`) but **no member identity**, which matters for any per-passage credit. A docket entry's `what_changed` quotes the edition's statement. It is a separate signed object, so AI provenance of a docket entry's own `summary` would need its own field.
- Unrelated namespaces: `NS_AI_RUN` (`bio-ai-run`) signs a test container's bundle (`sshsig.mjs:571`, `:774-777`). It is not about case content.

## 4. How a format change is handled

- **Versioning:** `CASE_DOCUMENT_FORMAT` is `bio-case-document/10`. `/9`…`/1` stay in `CASE_DOCUMENT_FORMATS_ACCEPTED`, "read as written" (`bio-plane/src/case-grammar/formats.mjs:42`, `:59-60`; CG R35, CG:200). `caseDocumentFormatFor` answers `/10` always (`formats.mjs:96`). Feature predicates are by format (`formats.mjs:64-84`, `:106-108`, `caseDocumentStatesUngradedAndTyped` for n ≥ 10).
- **Frozen bytes (CG R33, CG:184-194):** words a reader reads are chosen by the document's own format, never by the clock, release or word table. A render must give the same bytes for ever, offline. A rewording is a new format. Stored `/7` fixtures re-render to recorded SHA-256s. Any new **rendered** text for provenance in the complete edition (R14) is therefore format-bound and must be frozen in the module for that format.
- **Two precedents point in different directions:**
  1. **Additive and optional, no bump.** `account:`, `bias_applications:`, `review_comments:`, `approvals:` joined `/7` "optional, with no new format, as R10's `working_on` and R22's `subject_entity` are: a document without one reads null" (`account.mjs:7-8`). `calculations:` and `timeline:` joined `/7` with no `/8` (`formats.mjs:23-25`). Docket T45: `outcome` and `summary` added to `civicsmith-docket-entry/1` as additive fields, with older entries reading `outcome: null` (`docket.md:70`).
  2. **Bump when an old checker would give a wrong verdict.** G47: an attestation `sha` changes the checker's join, so it declared `/9` (`formats.mjs:30-35`; CG R1 last sentences). T53: typed passages would be read as quoted by an old checker, so `/10` (`formats.mjs:36-41`; CG R38 "because a checker pinned before the fields would ... give a wrong verdict", CG:203).
- **What an older peer does:**
  - **New format token** (`/11`): the gate's C-41 format check is an error for a format not in the accepted list (`bio-plane/src/case-catalogue/checks.mjs:541-542`). The checker runs that check (`case-checker/check.mjs:517`), and every error becomes a case-level `differs` (`check.mjs:522-523`), so every finding reads `did_not_recreate` (`case-checker.md:32` R11). case-import does not refuse on format. It refuses only on a manifest failure (`case-import.md:29-34` R1), then records the checker's result, so an older peer **imports the case but reports it as not recreated**. The product accepts this as stated: "A program handed out before T31 does not know `/7` … may report a newer case's complete edition as differing" (`case-checker.md:118`).
  - **Additive key inside `/10`, no bump:** no unknown-key refusal was found in case-catalogue, case-checker, case-import or record-grammar (grep for unknown/extra/allowed keys found nothing). The front matter grammar takes any flat rows (`document.mjs:11-13`). An old peer would therefore **accept and ignore** it, and the signature still verifies because the bytes are what was signed. The ignored data is lost to that peer, and its complete-edition re-render (`case-checker.md:31` R10) stays equal only if the new field changes nothing that `completeEditionOf` prints for `/10`. If provenance is to be **printed** in the complete edition, or **checked** (for example, a gate rule that a `machine_draft` row needs a draft id), the precedent in (2) calls for `/11`.
- `/10` readers state `predates` for older formats and never read a key early (`passages.mjs:95-106`). That is the pattern to copy, so absence in an older edition reads "not stated", never "human-written".

## 5. What is missing to produce per-passage provenance

1. **No stable identity for an authored sentence.** Only `ord` and `kind` exist (§2). Per-passage provenance keyed by `ord` holds for one edition only. To track a sentence across editions, or to link an AI event to a sentence, needs an id or a content hash per sentence.
2. **Only whole-account granularity.** Origin is set once for all account sentences from the draft's form (1.b). Nothing compares the member's sentences with the draft's sentences, so "this sentence kept from the draft, that one the member's" cannot be stated. Investigation's per-answer `kept: unchanged|edited` (1.o) is the one per-unit precedent.
3. **Writing help leaves no trace** (1.g, "It writes nothing of the record"). Text a member takes from a writing-help draft into the scope, what-changed or other own-words fields reaches the case as `member`. The door counts its usage (`ai-use`, keyed by act id, 1.p) but holds no link to the field or the resulting text.
4. **Most authored fields carry no origin:** scope, completeness statement, subject justification, exclusions, bias acknowledgement and outcomes are `member` by construction (`case-account/index.mjs:316-332`) or not recorded at all. The R23 rows for the statements copy their text, so a per-row origin field would cover them if it were filled honestly.
5. **Acceptance records do not name their result.** `acceptanceRecord` is `{proposal, form, by, at, kind}` (`acceptance.mjs:29-37`). The link to the accepted passage, leg or version lives in per-module tables, if anywhere, and none of it reaches the case document.
6. **No "human-reviewed" or "AI-assisted" value.** Today the vocabulary is `member`/`machine_draft` (+`adopted_as_drafted` for R8 only). There is no record of review apart from `typed_passages` checkers (source passages only) and approvals (whole document, CG R26).
7. **Findings' prose** (claims shown in "The Conclusions This Case Records", `document.mjs:312-335`) comes from the members' own conclusions. A machine may only suggest a basis version, carrying `run` in the finding's bytes (1.m). The case document does not carry that origin, and conclusions are machine-refused acts (`wizard-scripts.md:104` R24 item 2).
8. **Complete edition does not show origin** even where it is recorded (1.a). public-read exposes what-changed's `began_as` (1.e) but not the account's.

## Open questions and whose call

**Bob's (values and policy)**
- The vocabulary and its meaning. Is "AI-drafted, then edited by a member" AI-drafted or AI-assisted? Today it is `machine_draft` (account) vs `adopted_as_drafted` true/false (what changed). Does "human-reviewed" mean another member checked it (as `typed_passages` checkers do) or that the author read it?
- Whether provenance covers the case's own prose only, or also source-passage transcription (already partly in `chain`, 1.k) and docket entries' `summary`.
- Should AI-assisted text be allowed where unchanged adoption is refused today (account `ACCEPT_MUST_REAUTHOR`) but allowed elsewhere (what-changed `adopted_as_drafted: true`)? The two rules disagree.
- Credit: does provenance name members at their chosen attribution level (as R37 does) or only machine/human? The docket allows no member identity at all (`docket.md:68`).
- Is self-declaration acceptable where the product cannot observe the AI use (text pasted from an outside AI tool)?

**BOB's (requirements and plumbing)**
- Format: a new `/11` (printed and checked, precedent G47/T53) or optional rows within `/10` (precedent T41 `account:`). The choice decides old peers' verdicts (§4).
- A stable per-sentence identity (§5.1), and whether the existing `account:` `began_as` is extended per row or replaced.
- Writing help must record an acceptance linked to `(act, field)` and the resulting text hash (§5.3). The R24 tension on `publish` fields (refused) vs "a case's scope, what changed" (offered) needs resolving.
- `acceptanceRecord` gains a result link, or each module keeps one that case-authoring can read (§5.5).
- Checker and gate rules (for example, `machine_draft` requires a draft id that exists) and case-import recording, by R34's pattern (`case-import.md:167`).

**The lane's (design)**
- Where provenance lives: per-row fields on `account:` (covers the statements and outcomes too) vs a separate `authorship:` block keyed by sentence id, and how the complete edition and public read print it (frozen words per format, CG R33).
- How the reader sees it per passage: marks, a legend, or a section, and how "not stated" for older editions reads (copy the `predates`/`unreadable` sentence pattern, `passages.mjs:37-44`).
- How the signing ceremony shows the member what provenance they are about to sign (the R88 list is the pattern for "shown before signing, never blocks").
