What the plane is, in one paragraph

Civicsmith is built as about two hundred parts, called modules, in a fixed order; each part may only use parts before it. The plane is the launcher: the part near the end that starts every other part on one store and hands requests to the front door, so that a team runs one program on the hosting service. Its own code is small and decides nothing itself.

Why it has become a problem

27test files that check the plane itself
120test files it holds that check other parts
33–44 minto run its tests, against a 45 min limit

When the parts were put in order, any test that started the whole program was given to the plane, because only the last part may use everything. A test at the end finds a part's flaw late, after that part's own work has merged, and often not at all: the plane's tests run only when the plane has work. Measured counts; the timing of how flaws are found is read from the process design.

What the research found

None of the 120 needs the whole program. Each was read and classed by what it tests, why it loads a later part today, and how it can be rebuilt not to. Every one can run in the part it proves, or in an earlier part, without a hand-made stand-in. 17 were moved or rebuilt on scratch copies and pass there, with the process's order check clean. No test was left without a route.

  • Most run as ordinary tests in the part they prove: 157 of the 207 tests and files counted.
  • 19 need the real hosting runtime, and get it through a small test-only store built from earlier parts.
  • 19 must be rebuilt so they no longer load a later part; each has a route.
  • 12 are duplicates and can be dropped; nine of them are old suites already ruled for deletion.

The research counts the front door's 46 files by test (133) and the rest by file; the report gives the table.

One piece moves with them. 86 of the front door's tests need the code that decides which part answers each request. That code sits in the plane today. Moved unchanged into the front door, it lets the door's own tests use the real thing: all 569 of the door's tests passed on a scratch copy, and the built program was byte for byte the same. Measured.

A correction. An earlier version of this page said these tests could not move earlier than the plane without testing a copy of the program. Reading each test showed otherwise.

The lane's recommendation

Prove each part's promises in its own tests. Each whole-program test moves to the part it proves, rebuilt where it now loads a later part. The plane keeps only its own 27. Checking parts at the end of the order (the earlier choice B) are made only for a test whose route fails when it is built; none is planned.

This goes together with the layers work you asked about: the capture move, the front door taking its screens from outside, and the front door and launcher moving below the screens. The screens' own tests can then use the real front door.

The plan, in eight steps

  1. The capture screen's two document functions move below the front door.
  2. The launcher's routing moves into the front door.
  3. Each whole-program test moves to the part it proves, as a new file there; the old file is then removed; duplicates are dropped.
  4. Two requirement files that are too large to read whole are split.
  5. The front door takes its screens from outside and stops importing them.
  6. A small top part plugs the screens into the launcher. It owns the deployment file, the build script and the built program, and holds the tests that start the whole program.
  7. The written promises that state today's order are reworded, and the front door and launcher move below the screens.
  8. Follow-ons, each small: build and test tools that read every part move to the end of the order, or the release part; the screens' tests use the real front door; shared addresses and words are written once.

Each step is merged on its own. The full table, with why each step can merge alone, is in the layers research report.
