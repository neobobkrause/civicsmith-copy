What the plane is, in one paragraph

Civicsmith is built as about two hundred parts, called modules, in a fixed order; each part may only use parts before it. The plane is the part near the end that puts all the others together into the one program a team actually runs on the hosting service. Its own code is small: it starts every other part on one store, hands requests to the front door, and wakes the scheduler. It decides nothing itself.

Why it has become a problem

105test entries given to it
171other parts it says it uses
33–44 minto run its tests, against a 45 min limit

When the parts were put in order, any test that starts the whole program was given to the plane, because only the last part may use everything. Many of those tests were written to prove other parts' promises. So the plane carries other parts' proof, its test run is close to the time limit, and a change to any of those other parts is not proven when that part's own work runs.

What its tests actually are

Plane's run holds 147 tests. Only 27 check plane itself. The other 120:

  • 27 check how other parts behave on the real hosting program: very large files, memory, timers that wake the program.
  • 86 walk through the real front door to check other parts' promises. More than half were written for the front door's own part; the rest for the screens and a dozen others.
  • 7 odd ones, among them the check that stores saved by every earlier release still open.

A correction to what I told you earlier. I expected many of these tests could go back to the parts they test. The measurement says otherwise: 138 of the 147 start plane's own program, 108 of them on the real hosting runtime. They cannot move earlier than plane without testing a copy of the program instead of the real one, which would undo your ruling that anything depending on the live service is checked on the real thing.

So the fault is where the tests sit, not that they exist: they belong at the end of the order, but not inside plane.

The choices

A. Leave them in plane, and make the run faster

Gives: the least change. Costs: plane stays answerable for 120 tests about other parts. Its run stays near the limit and grows with every new whole-program test. A change to plane's few hundred lines still reruns everything.

B. Plane keeps only its own 27; the rest move to new checking parts placed right after plane

Two new parts at the end: one for behaviour on the real hosting program (with the old-stores check), one for the walks through the front door. ARCH can split them further if a run is still long.

Gives: plane's own run takes minutes. Each checking run stays well under the limit (expected from the measured shares; not yet measured). A failure lands on the part whose job is that check, which reports the faulty part to ARCH, as any work does. Costs: two or more new parts, and moved requirement text: ARCH's work. Each such promise is written twice, once at its owner and once as a whole-program check. The owner part's own work still does not run the whole-program check; the checking part runs it when something it uses changes, and the walks cover the rest. That the process tool spots those changes inside such a part is not yet proven.

C. Rewrite the tests so each part checks itself with stand-ins

Gives: each part's own work proves its own promises. Costs: rewriting up to 86 tests, about 14,000 lines. A stand-in can drift from the real thing, so the real-program checks must stay at the end anyway. It narrows your real-hosting ruling.

The lane's recommendation: B

It returns plane to its purpose at once, takes its run far from the limit, and keeps every check on the real program, as you ruled. C stays open part by part: where a part can prove its own promise in its own tests without a stand-in that drifts, its work does so, and the whole-program check stays at the end beside it.

What B means once built (ARCH's answer, 23 Nov)

ARCH, which decides the order of parts and builds it, says B can be built as given, on these terms:

  • Place. The new parts sit right after plane, before the release part: first the real-hosting check part, then the front-door walks. Plan for the walks to be two parts from the start, since the front door's own 46 tests are most of them; ARCH splits further if any run passes about 20 minutes.
  • Promises. Every test there checks a promise written in its own part, and each such promise names the original promise it carries. ARCH writes them. A test without one stays with its owner part or goes to ARCH.
  • Code. The shared test helpers become their code. No file moves on disk; only who owns it changes.
  • The plain cost. These parts use nearly every part before them, so nearly any change to another part's interface gives them work: frequent short jobs that rerun their whole set. That is the price of keeping whole-program checks in one place. C avoids it, but loses the real-hosting checks.
  • Open points. Run times are known only after the first runs. Whether 10 of the platform tests can go back further, to the part that builds the store, ARCH settles when it builds this.
  • When. Nothing is built while your halt stands, and not before you choose. On B, ARCH changes the order of parts in one step and rewrites plane's description; plane's open work then keeps only its own 27 tests.

Whichever you choose, plane's own description is corrected: it still describes work that moved to another part in October.

Not yet known: the exact run time of each new part; whether 10 of the platform tests need plane at all; and whether the 45-minute limit itself changes, which is with PROCESS and you, not this lane.

The layers you asked about: a second choice

On 23 November you asked to see civicsmith as five layers, stacked model, middleware, front door, launcher, UI, and what it would take to stack the code that way. Today the front door and the launcher (plane) sit above the screens. The full findings, the case for and against, and a step-by-step plan are in the layers research report.

  • It can be done, and it was tried. On a scratch copy the front door and the launcher stopped importing any screen code, and the screens were plugged in from one small part at the top. Every test set run passed as before. Users were sent byte-for-byte the same pages. Measured.
  • It does not fix plane's scope on its own. The whole-program tests still need a home at the end, which is what B gives them. Doing B first cuts the tests the re-stacking must move from 121 to about 27 (worked out, not run).
  • Its main cost is paperwork. 163 written promises in 26 parts state today's order; about 112 are likely to need rewording, which is ARCH's work. Measured count; the 112 is a judgment.
  • One small step is worth taking either way. Moving the capture screen's two document functions below the front door changes 4 files, leaves the page byte-identical, and removes the only place background work runs screen code. Measured.

The lane's recommendation

Choose B now, with the capture move. Choose the re-stacking separately, when you want it: ARCH can build it after B in small steps, each merged on its own.
