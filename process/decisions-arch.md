# civicsmith: ARCH's technical decisions

Written only by ARCH (Process4 build text 2, section 8). One entry for each subject; a changed decision rewrites its entry in place. Each decision is one pull request. The `Decision` line is the plain line the coordinator gives the owner.

## Requirements: place and form
Decision: each module's requirements move from `build/requirements/<module>.md` into `process/modules/<module>.md`, in Process4's form. Each live requirement becomes one line, `- **R<n>** [met]` or `- **R<n>** [not yet met]`, with its number and words unchanged, under the same headings as before. A requirement the old file marks "not yet met" stays not yet met, and every other live one is met. Retired numbers are deleted, and `Next number` is set above the highest number ever used. The module's purpose, uses, invariants, suggestions and the canon it satisfies are carried as they are. The old "Open for Bob" sections are not carried: ARCH decides each technical item in this record, and any item that is the owner's goes to him through the coordinator. A module whose converted file would pass 60,000 bytes is split into two real modules before its first job. The old files stay in `build/` as history.
Why: Process4 reads a module's work from that one file alone. No module has one yet, so no module has work, and nothing can be placed until they exist.
Decided: 22 Nov 2026.

## Module list: order and ownership
Decision: the module list is corrected so that every module, its tests included, uses only modules before it. A new first module, `documents`, holds the product's documents and the earlier processes' records (`docs/`, `build/`, `requirements/` and the top-level files), with no product code; the earlier processes' scripts in `build/plan/`, `build/tools/` and under `docs/` go to `journey-check`, the last module, except the word-table list `docs/development/ux-substrate/screens/build_words.mjs`, which imports nothing of the product and is read as text by `site`'s tests. `op-grades` moves to just before `member-roster`. `bundler` is split: it keeps the generic bundling recipe, and a new module, `release`, just after `plane`, takes the deploy, release and bundles scripts, `release/`, the three release workflows and the fleet's tests, with bundler's requirements on them (R12, R17 to R23, R25 to R37, R39 to R42, numbers kept); `build-plane.mjs` and `bio-plane/dist/` go to `plane`, with bundler's R16 as plane's R115. `bio-plane/package.json` and its lock file go to `test-support`. 213 test files are given, by naming their paths, to the module that comes after everything they reach: whole-plane tests to `plane`, whole-product walks to `journey-check`, the declared-operations registry tests to `store-assembly`, the screen census to `control-plane`, and the rest as their imports require; each module's `uses` names what its own code and tests import. Twelve pieces of code work that would let some of those tests return to the module they test are owed to named modules' jobs, and are placed once jobs run.
Why: the list converted from the earlier process had tests reaching later modules in thirteen groups, and documents owned by the last module, so most modules' tests reached the end of the order. The order rule is part of every module's tests; a list that breaks it fails every job.
Decided: 22 Nov 2026.

## Module splits for size
Decision: 23 modules whose requirements passed 60,000 bytes are each split along an existing file boundary, the new part placed just before the module it came from, which uses it; requirement lines move whole with their numbers, and both parts keep the original's `Next number`. The new parts: jurisdiction-profiles, op-grade-tranches, credentials-tables, provenance-register, record-core-tables, contradiction-words, agent-worker-routes, case-document, filing-texts, wizard-library, act-help, queue-words, queue-catalogue, store-services, screens-account, screens-capture, screens-find, screens-document and screens-question (screens-inquiry is in three parts), screens-people, screens-public, screens-send, installer-account, installer-pages (204 modules). The new parts have no tests of their own yet: their tests enter through the original's front file and stay with the original until each part's job gives it its own. Ten modules cannot be split without dividing one large code file (actions, instance-setup, op-declarations, member-roster, acquisition, capture, reading-pipeline, extraction, interface-shell, control-plane); each one's job first moves a part out of that file, and the split follows.
Why: a requirements file over the single-text maximum cannot be read whole by the job that must follow it (Process4 design part 5).
Decided: 22 Nov 2026.

## The walks' commands and development copies
Decision: the walks and the development deployment use four commands the product does not yet have, written as requirements not yet met, and the process config names them now. In `release`: one script, `node bio-plane/scripts/dev-copy.mjs`, with `deploy <copy>`, `seed <copy>` and `remove <copy>`. `deploy` builds the plane and the fleet from the checkout, unsigned, and puts up a whole copy under names made from `<copy>` and kept apart from any installed site's, with a small documents site of its own serving the documents the journeys capture (walks index, section 7, item 1, the amended notice of J23 among them); `seed` gives the copy the starting data the walks index names (section 5) through the plane's own admin operations, making no member and no sign-in; `remove` deletes everything named for that copy and reads back that nothing of it remains. All three act only in the development account the process config names, refuse any other before a request, make any instance value fresh for the copy and never print or commit it, and each step fits in one command of under thirty minutes. In `journey-check`: `node bio-plane/src/journey-check/steps.mjs <address> <step file>...` runs the named walk steps against an address, in the order given, and prints for each its header lines and what it saw; a sign-in a step makes through the copy's first-use door is kept only outside the repository for that run. `walk.build_and_serve` stays as it is. The journeys that install (J01, J28, J29) are named as areas only when no other copy stands in the account, and are walked one at a time. Time passing (J18, J19) is left out of the areas until a designed way to make it happen exists.
Why: the config named commands that walk every journey without taking an address, and no command deployed, seeded or removed a copy by name; a walk cannot be made with them (build text 3, sections 4 and 5).
Decided: 22 Nov 2026.

## Committed built files
Decision: the built files that stop being committed are the bundles: each fleet member's `dist/` (agent-runner, agent-worker, file-scanner, ocr-worker, pdf-worker, sheet-worker), the plane's `bio-plane/dist/` bundle and manifest, and the installer's `newgroup/dist/`. Each such folder keeps only a committed `.gitignore` that ignores everything else in it; the bundle is built there by its own module's build script whenever a test, a deployment or a release needs it, and the release tooling builds every bundle afresh and never reads or copies a committed one. Generated sources that product code imports (`setup-words/rows.mjs`, `court-citations/court-data.mjs`, `member-roster/order.mjs`, `case-checker/program.mjs`, `agent-runner/src/says-words.mjs`, the three `wizard-scripts` data files, `ocr-worker/src/tesslib.mjs`, `sheet-worker/src/enginelib*.mjs`, `interface-assets/index.mjs`, `site/src/pages.mjs`) are source of the module that owns them: they stay committed, each changes only by its own module's job running its generator, and its module's own tests keep it current. `release/` and `newgroup/src/release.mjs` are the signed release and its embedded copy: they stay committed and change only in the release ceremony. `bio-plane/dist/SECRETS.txt` is kept by hand, not built; it moves to `bio-plane/SECRETS.txt`, owned by `plane`, by a mechanical edit that also changes the paths its readers use. Order of landing: the mechanical edit first; then release R46, so nothing reads a committed bundle; then each bundle's own module removes its committed copy, in any order (agent-runner R43, agent-worker R120, file-scanner R36, ocr-worker R32, pdf-worker R45, sheet-worker R18, plane R116, installer R86).
Why: the design says built files are never committed (part 2, section 6). A bundle is rebuilt from the checkout in seconds by its own module, which comes after `bundler` in the order. A generated source is imported by product code at load, and the required run has no build step: the only code run before every module's tests is `test-support`'s, which comes before most generators in the order; and some cannot be rebuilt on a test machine at all (the spreadsheet engine's glue needs Rust; `interface-assets` and `site` read a past commit a shallow checkout lacks; the installer's copy embeds the signed release). Removing `release/` would stop installed sites finding updates. This rewrites the decision of 22 Nov, which had every generated source stop being committed.
Decided: 22 Nov 2026.

## Code differences found before the first walk
Decision: the 90 differences between the code and the Screens pages that the UX lane found by reading the code (87 listed on the screen pages, three more in its decisions U11 and U12) are judged by the ranking page before any walk. Where a requirement backs what the code does, the page is wrong, because requirements rank above design decisions, and the UX lane corrects the page now, while no tranche is open (36). Where no requirement names the words or label at stake and the code's behaviour is backed, the lane may take the code's words or name a reason to change them (16). Where a requirement backs the page, or no requirement covers what the page draws and the page does not mark it "not built", the product is wrong: each is placed in the waiting-work record against the module that owns the code, as a flaw from ARCH, and becomes that module's work in the first round (29, in 14 modules). Parts the page marks "not built" with no requirement behind them, among them the seven AI screens no module owns, are left out of the first tranche until ARCH writes their requirements (10). Capture's fetch refusals keep the shared `refusal.<code>` words, as `screens-capture` R45 says; the lane's U12 gives way to it there. Signing out goes to the team's page, as the code does; the word row it draws still says "the sign-in page", so `setup-words` rewords it and retires the two rows nothing reads.
Why: the walks are measured against the pages, so a page that differs from a met requirement would turn each walk into a flaw that is not one; and a difference known now costs a round less if it is placed now than if a walk finds it.
Decided: 22 Nov 2026.
